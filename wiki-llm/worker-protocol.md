# Provider WebSocket protocol (v1)

Endpoint `GET /v1/worker` on the api's public URL (`API_PUBLIC_URL`, scheme `ws`/`wss`). The upgrade is refused with 403 unless its `Origin` header equals `WEB_ORIGIN`; any other path gets 404. JSON text frames, one object per frame, each with a `type`. Every inbound frame is validated with zod; an invalid frame closes the socket (4400). Max inbound frame 64 KiB (larger: close 1009); binary frames close 4400. Strings and numbers in every frame are bounded (e.g. `chunk.delta` at most 16 384 characters, `finishReason` is `stop` | `length` | `abort`, token counts integers up to 10^9); frames carry no unknown keys.

## Sequence

1. Browser gets a worker token: `POST /api/worker-token` (session).
2. Opens the socket; first frame within 5 s: `auth { token, protocol: 1, deviceKey }`. `deviceKey` is 8-64 characters `[A-Za-z0-9_-]`, a random id the browser keeps in `localStorage` (identifies the device row in `workers`). Bad, expired or used token, or a suspended user → close 4401. The server upserts the `workers` row (`user_id`, `device_key`, `last_seen_at`) and registers the worker as `connected`.
3. Server: `welcome { workerId }` (the `workers` row id). The worker waits for it before sending anything else.
4. `ready { model, gpu: { vendor, architecture, shaderF16, maxBufferSize }, loadMs, contextWindow? }` within 60 s of `welcome` (else 4408). `model` (at most 256 characters) is the `gguf_ref` of an enabled catalog row; unknown or disabled → close 4404. The worker has already loaded the model and run one tiny warm-up generation (D36) **before connecting**: a cold download can outlast the 60 s token. The server stores `gpu` and `last_model` on the row; `gpu.vendor` and `gpu.architecture` are shown publicly, so they are cleaned first (only `A-Za-z0-9 ._()+-`, spaces collapsed, at most 48 characters); the worker is now `ready` (idle). A second `ready` closes 4400. `contextWindow` (optional, integer 256-1 048 576) is the context window the worker loaded; omitted by tabs from before it existed, which are treated as 4096. The api only offers a worker jobs (prompt estimate + `max_tokens`) that fit it.
5. Worker sends `heartbeat {}` every 5 s. Silent for more than 15 s → server drops it (close 4408; swept every 5 s). `workers.last_seen_at` is written at most once a minute. The server answers each heartbeat of the device's current socket with `pong {}`; a worker that has already received a `pong` on its socket and then hears no frame for 15 s treats the socket as dead (it may be half-open after the machine slept, a tab freeze or a network change), abandons it without waiting for a close event and reconnects at once with the backoff reset. Tabs from before `pong` ignore it; a worker never declares a socket dead before its first `pong`, so an api from before `pong` is not flapped. A token request the page does not answer within 15 s is abandoned and retried.

Close codes: 4400 invalid frame or sequence, 4401 auth (timeout, bad token), 4403 owner suspended (found at the once-a-minute heartbeat check; the worker is then also skipped for jobs), 4404 unknown model, 4408 timeout (no `ready`, or silent), 4409 replaced by a newer connection of the same device, 4413 backlog (more than 1 MiB of frames received but not yet processed on one socket; retryable), 4429 too many workers (4 per user, 5 000 in total). A device that reconnects (same `deviceKey`) replaces its old entry: the old socket is closed 4409 and never counts twice, and anything the replaced socket still sends is ignored. A socket that closes while its `auth` is being processed never reaches the registry.

Pre-auth budget: at most 300 sockets may be connected without having authenticated (counted from the upgrade until `auth` succeeds or the socket closes); beyond that the upgrade is refused 503. Per-IP rule: at most 30 upgrades per minute per IP, refused `429` at the upgrade (the socket address, or `X-Real-IP` when `TRUST_PROXY=true`; [api.md](api.md) "Limits"); the browser's reconnect backoff handles it. In production the page on the web origin connects cross-origin to the api host; the `Origin` check against `WEB_ORIGIN` is what admits it.

Wake-up: the page tells the worker (`wake`) when the tab becomes visible, the page resumes (`resume`, `pageshow`) or the network returns (`online`); the worker then heartbeats immediately and replaces the socket if no frame arrives within 4 s, or, when it was between connections, skips the rest of the backoff.

Engine recovery: three consecutive jobs that fail with an engine exception (any error except a cancel or a prompt over the context window; only a successful job resets the count) make the worker close its socket, reload the model and reconnect, instead of staying online and failing every job. A job that has not settled 25 s after an abort (`ABORT_WATCHDOG_MS`, under the api's 30 s cancel grace; the engine only sees an abort between 512-token batches) is treated as a hung engine and triggers the same reload.

Reconnect (browser): after any close the page requests a new token and the worker reconnects with exponential backoff (1 s doubling to 30 s, jittered by +-50%; the counter restarts only after a connection stayed up 30 s) without reloading the model; 4400, 4404, 4409 and 4429 are not retried (4403 closes mean the account is suspended; the page's next token request then fails and it stops).

## Jobs (one at a time per worker)

| Direction       | Frame                                                                                                                                                                                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| server → worker | `job { id, messages, params }` — params: `temperature`, `top_p`, `max_tokens`, `stop`, `presence_penalty`, `frequency_penalty`, `seed`, `enable_thinking`                                                                                                                       |
| worker → server | `chunk { id, delta }` — text; reasoning as `<think>…</think>` (see below)                                                                                                                                                                                                       |
| worker → server | `done { id, finishReason, usage: { promptTokens, completionTokens, decodeTokensPerS } }`                                                                                                                                                                                        |
| worker → server | `error { id, code, message }`                                                                                                                                                                                                                                                   |
| server → worker | `cancel { id }` — worker aborts the engine's generation                                                                                                                                                                                                                         |
| server → worker | `stats { jobsServed, promptTokens, completionTokens, creditsEarned, lastJob: { promptTokens, completionTokens, decodeTokensPerS, credits } }` (the four totals are the account's lifetime numbers; the page shows the session by summing each `lastJob`) after each settled job |

- No KV reuse between jobs (D27): every job runs with `cache_prompt: false` and one slot (`n_parallel: 1`).
- The worker passes the params to wllama's OpenAI-style `createChatCompletion` (`stop`, `presence_penalty` and `frequency_penalty` are not in its types but pass through); it streams with `stream_options.include_usage`.
- **Thinking per model family** (`libs/wllama-webgpu/src/profiles.js`): the engine picks an adapter from the loaded GGUF's `general.architecture` (unknown: default) and maps `enable_thinking` to the variable that family's chat template reads, and its reasoning markup to the `<think>…</think>` the api parses (D31). Chunks always carry that form and never a family marker; markers split across deltas are buffered, and only the first reasoning block of a reply is wrapped.

  | Architecture (models)     | `enable_thinking` becomes                                             | Raw reasoning markup → chunk text                                                                                                                               |
  | ------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | default (Qwen3.5)         | `chat_template_kwargs.enable_thinking` (omitted when unset)           | `<think>…</think>`, unchanged                                                                                                                                   |
  | `gemma4`                  | `chat_template_kwargs.enable_thinking` (template default off)         | `<\|channel>thought\n` → `<think>`, `<channel\|>` → `</think>`; `<turn\|>` dropped                                                                              |
  | `inkling2_loop` (Inkling) | `false` → `reasoning_effort: "minimal"`; `true` or unset → `"medium"` | `<\|content_thinking\|>` → `<think>`, `<\|end_message\|>` → `</think>`; `<\|message_model\|>`, `<\|content_text\|>`, `<\|content_model_end_sampling\|>` dropped |

  Inkling's template ignores `enable_thinking` and cannot switch reasoning off, so its output always opens with a `<think>` block (billed as output, D28). Thinking on or unset asks for `medium` because the template's default `high` reasons too long for a x3 model; the api moves it to `reasoning_content`.

- A template with thinking off may emit an empty `<think></think>` block before prefill ends (Qwen). The engine holds back any normalised text that can still become an empty think block until real output arrives, so scaffolding never reaches the api early and cannot satisfy the first-chunk timer. Reasoning text itself is real output and is forwarded as soon as it starts.
- wllama drops its final usage when a generation is aborted: on abort the worker reports the prompt tokens seen in prefill progress and the raw tokens it generated (each streamed wllama token, whatever the profile forwards) instead.
- Frames for an unknown or finished job id, or for a job the worker does not currently hold, are ignored. A second `job` while busy is a server bug: the worker answers `error { code: "busy" }`.
- A worker stays busy until it sends `done` or `error` for its job id, also after the api sent `cancel` (consumer left, first-chunk or total timeout (600 s API, 300 s Playground), output over the limit). The worker should answer a `cancel` promptly with `done { finishReason: "abort" }` (or `error`); if it sends neither within 30 s (an abort is seen only between prefill batches, which can take 10 s or more on a slow GPU) the api drops its socket (close 4408). `done` with `finishReason: "abort"` for a job that was not cancelled, or with no (or only whitespace) output, counts as a failure. After a consumer cancel that followed delivered output, the `done` usage is what gets billed (capped at the chunks delivered + 8, [economy.md](economy.md)). `stats` totals are integers up to 2^53-1. Output beyond `max_tokens` + 8 chunks or 64 characters per `max_tokens` is cut off the same way.
- Usage in `done` is capped before settlement ([economy.md](economy.md)); `stats` follows each settled job.
- The provider UI shows live usage from `stats`; it never receives consumer identity.
